# Bugfix Requirements Document

## Introduction

This document records the result of a full defect audit of the OOJ automation project (`tools/`, `tools/web/`, `tests/`, the Excel template `Docs/Templete_OOJ Process_Date_September_KABIDEBA.xltx`), with special attention to the changes made this session (two-phase SCC upload, fresh-run wipe, Desktop export naming, CX Address Check column, the self-contained column-P formula, the `approval_in_comments` column and the app-mode browser launch). The audit read every live module, ran the test suite (`C:\Windows\py.exe -3.13 -m pytest tests -q` → 94 passed, the expected baseline), probed the real template and the real completed run `tools/captures/runs/20261028_152733_335009` (1494 Tech_Data rows, Phase A 15:27 → Phase B 16:05, full ADS-approved run that was published to the Desktop), and inspected the operator's Desktop and Downloads folders.

Nineteen genuine defects were found. One is data-corrupting (1.1: 48 of 1494 remarks in the real run are `#N/A` where the rules say they must be "Invalid - It is Inside Jurisdiction as per GCRS Tool" or "Valid"), one writes confidently wrong advisory text (1.2: 69 of 70 "PIN does not serve X" verdicts in the real run are false), two can delete the operator's own data (1.3 the manual SCC export in Downloads, 1.4 the post-comments audit reports), several are state-machine/UI gaps introduced by the new pause-and-resume design (1.5–1.10), and the rest are low-severity latent, cosmetic, portability or performance defects (1.11–1.19). No defect was found in the standing-rule areas: PNAMA/DSR stay serial on one Edge profile with the 2-attempt refresh, GRBI stays sequential, polygon fetch is single-attempt, ADS is a single upload whose first column is `TrackingId`, EagleEye is API-only, `COLUMNS_TO_REMOVE` is `[]`, `preflight_state()` keys were only added, KABIDEBA branding is intact in `index.html`, the `server.py` banner and the published filename, and no live code references the deleted `scc_client`/`lane_scc`/`apply_remarks` stage/old `OOJ_Process_Filled_` name/removed element ids.

Audited and found clean (code-verified unless stated): the combined P formula is parenthesis-balanced, 2,936–3,086 characters after row translation (Excel limit 8,192), keeps `_xlfn.`, keeps the template's array-formula kind, and the `Translator` shifts `J/AF/AG` and the embedded `E/J/N/O/R/S/V` references consistently while leaving the `"HYT2"` string literal untouched; `read_back`'s containment check passed against the real Excel-recalculated workbook. Working Sheet row r ↔ Tech_Data row r ↔ `tech_rows[r-2]` (template `A2=Tech_Data!B2`, `D2=Tech_Data!G2`), and the real run's polygon rows are TID-aligned 1494/1494. `FINAL_COLUMNS` are present exactly once in both the template and the real output; `AH`/`AI` are additive and empty in the template; the template's Working Sheet has no auto-filter so the `A1:AG` ref is never applied. `wipe_old_runs` preserves the current run directory via `resolve()`, keeps `scc_enum_map.json`, matches only `Templete_OOJ Process_*.xlsx` on the Desktop (the `.xltx` template that sits on the operator's Desktop is not matched) and its prefix equals `publish_to_desktop`'s real output name `Templete_OOJ Process_October_KABIDEBA1_<stamp>.xlsx`. Phase B reloads tech rows including `approval_in_comments`, the ordered `tids.txt`, re-applies the Start flags through `_build_ads_flags`, never wipes, re-arms the stdout drain and does not overwrite the captured `RUN_DIR`; a fresh Start clears any stale upload path. `is_publishable`/`is_downloadable` gate on exactly the stage names and the `polygon.verification.verify_ok` path that `run_daily` writes. `csv_safe` never alters any Phase A Tech_Data field; `str(datetime)` with microseconds round-trips through `fromisoformat`. `server.py`'s `/scc/upload` validates base64 and returns 409 on rejection; `_open_browser` de-duplicates and existence-checks candidates with a `webbrowser` fallback; `_relaunch_server` passes paths with spaces as list arguments. No `shapely` import exists (in-house point-in-polygon). Hard-coded machine paths (`builder-mcp.exe`, `mcscli.exe`, the Edge profile default) are portability notes only and cause no failure on the operator's machine. Not verifiable in this environment: live Midway/SIM-T/SCC/QuickSight/SIW/ADS/Excel-COM behaviour, the console-less relaunched server, and the exact on-screen sequence of the Phase A failure path (1.5), whose logic is nevertheless deterministic from the code.

## Bug Analysis

### Current Behavior (Defect)

Severity and verification status are stated per clause. "Code-verified" means the failure condition is established from the source; "evidence-verified" means it was additionally reproduced from the real run artifacts of 2026-10-28.

1.1 WHEN a Working Sheet row reaches the AF→AG→Valid block of the combined column-P formula built in `fill_template.extend_working_sheet` (`_afag_resolve`), i.e. the embedded template formula yields an "LM to reattempt" text or `#N/A`, AND column AF (`Station Transfer Validation`, a VLOOKUP into `Missort Data`) is the `#N/A` error because PNAMA returned no row for that TID THEN the system writes `#N/A` into column P (Remark), because `OR(AF2="…",AF2="…")` and `IF(…)` propagate the `#N/A` error instead of treating a missing AF as "not a transfer verdict" the way `remark_rules.decide_remark` does. Severity: critical — wrong final remark in the delivered workbook; in the real run 48 of 1494 rows (every one of the 48 has AF=`#N/A` and a valid AG value) were published as `#N/A` where the rules give 38 × "Invalid - It is Inside Jurisdiction as per GCRS Tool" and 10 × "Valid"; the same error propagation applies to AG when AG is a `#N/A` VLOOKUP in a run whose polygon lane was skipped or left blank. Code-verified and evidence-verified.

1.2 WHEN `polygon_check.analyze_cx_address` evaluates the PIN-zone vs. address-state rule and the GCRS/SIW `State` field holds a 2-letter state code that is absent from `_PIN_ZONE_STATES` (observed: `PB`, `DL`, `KL`, `TG`, `TL`, `BR`, `MH`, `HR`, `RJ`) or holds a city/district name instead of a state (observed: `Bengaluru`, `Dehradun`, `Ludhiana`, `Kolkata`, `Mohali`, `ZIRAKPUR`, `Gautam Buddha Nagar`) THEN the system writes a hard verdict `MISMATCH — PIN <pin> (zone <d>) does not serve <State> (…)` into the "CX Address Check" column (Working Sheet AH and the `GCRS Agentspaces` sheet) for a PIN that correctly serves that address, because `_fuzzy_same` only matches the full state name or a handful of ad-hoc abbreviations. Severity: medium — wrong advisory data; in the real run 70 such verdicts were written and 69 are false positives (e.g. TID 374734082992, PIN 560076, State "Bengaluru"; TID 374803703025, PIN 248197, State "Dehradun"; 22 rows with `PB`). The Inside/Outside status and the Remark are not affected. Code-verified and evidence-verified.

1.3 WHEN the local web server starts (`Start OOJ Web.bat` → `server.main` → `_sanitize("startup")`) or is restarted (`/restart` → `_relaunch_server` → `_sanitize("restart")`) while the operator's manually exported SCC file (SCC's native export name `SearchResults.csv`, present today as `C:\Users\kabideba\Downloads\SearchResults.csv`) sits in `~/Downloads` and has not yet been uploaded THEN the system deletes that file, because `sanitize_captures._DOWNLOAD_LEFTOVER_RE` still treats `SearchResults*.csv` as an automation leftover of the retired SCC browser lane. Severity: medium — destroys the operator's manual work product; the operator must redo the SCC search/export. Code-verified; the file's presence on the operator's machine is observed.

1.4 WHEN a fresh run starts (Phase A, `run_daily.wipe_old_runs`) THEN the system deletes every file under every `tools/captures/<folder>/` other than `runs/` and `scc_enum_map.json`, which includes the post-comments feature's uploads (`captures/post_comments/uploads/*`), its dry-run summaries and its `post_comments_report.xlsx` files — the only record of which live, irreversible SIM-T comments were posted — and would also delete the input workbook of a post-comments dry-run that is in progress (post-comments blocks itself while the pipeline runs, but `start_run` does not check post-comments). Severity: medium — loss of audit data; evidence: every `captures/post_comments/<stamp>/` folder older than the last Phase A (e.g. `20261013_210249_723757`) is now empty while the one created after it still holds its report. Code-verified and evidence-verified.

1.5 WHEN Phase A (`run_daily.py --stop-after-tickets`) exits with a non-zero code (preflight failure such as an expired Midway session or a busy Edge profile, an incomplete/failed SIM-T pull, or a crash before `RUN_DIR=` is printed) THEN the system keeps `RunController._phase == "awaiting_scc_upload"` (the phase is set at spawn and never reconciled with the exit code), so `/status` reports a paused run, `app.js` shows "Paused — upload SCC's export CSV in the SCC card (step 2) to resume the run." with the upload control, `tick()` never reaches its finish branch, both Start and Stop stay disabled, and `upload_scc_csv` accepts an upload (its guard only checks "not running, run dir resolved, phase awaiting") after which `continue_after_scc` spawns Phase B, which dies with an unhandled `FileNotFoundError` in `load_tech_data` because `tech_data.csv` was never written. Severity: medium — the operator is shown a false "paused" state and has no in-page way out except "Restart server". Code-verified (deterministic from `run_controller.start_run`/`upload_scc_csv`/`get_status` and `app.js tick/renderFinish`); the on-screen sequence needs a live confirmation.

1.6 WHEN the operator uploads the SCC CSV after a pause of arbitrary length (30 minutes in the real run) THEN the system resumes Phase B without any preflight: `continue_after_scc` does not call `preflight_state()` and `run_daily` runs `preflight` only in Phase A, so a Midway session that expired during the pause or an Edge automation-profile window the operator opened during the pause (for example to perform the manual SCC search in the signed-in profile, as the standing rules require signing in there) is not detected; PNAMA/DSR then fail inside the browser worker with a Playwright profile-lock error and EagleEye/GCRS with authentication errors instead of the clear "Edge automation profile is already in use" / "Midway session expired" preflight message a single-shot run produced. Additionally `post_comments_controller._pipeline_running()` relies on `rc.CONTROLLER.is_running()`, which is False during the pause, so a live comment-posting run may be started while the OOJ run is merely paused and will collide on the same Edge profile when Phase B resumes. Severity: medium — run failure (blocked or PARTIAL) with an unclear cause, recoverable by rerunning. Code-verified; exact failure text needs a live run.

1.7 WHEN Phase B starts (`run_daily.main` with `--resume-dir` constructs a fresh `Run`, whose `summary` is `{"stamp","schema_version","stages": {}}`) and performs its first `write_progress()` THEN the system overwrites `summary.json`, dropping the `preflight` and `tickets` stages and the top-level `tickets` counts that Phase A recorded, so `_sources_from_summary` reports the "SIM-T Tickets" card as `pending` with 0 % for the rest of the run and in the final state (the real run's final `summary.json` has no `tickets` key and no `preflight`/`tickets` stage). Severity: low–medium — misleading progress/final display; the workbook itself is unaffected because tech rows are reloaded from `tech_data.csv`. Code-verified and evidence-verified.

1.8 WHEN the run is paused awaiting the SCC upload THEN the system disables the Stop button (`app.js tick()` sets `stop-btn.disabled = !status.running`) and never re-enables Start (`refreshPreflight` is skipped while `runActive` is true), and a direct `/stop` returns HTTP 409 with `stopped: false` ("No run is in progress") even though `RunController.stop_run` resets `_phase` to `idle` specifically for this case, so the documented "stop while paused → Start offered again" path is unreachable from the UI. Severity: low–medium — the operator cannot abandon a paused run without restarting the server. Code-verified.

1.9 WHEN the page is reloaded or the app window is reopened while a run is paused (or running) THEN the system shows an empty, idle page: `app.js` boot only calls `refreshPreflight()` and never `tick()`, so the sources, log, SCC upload control and paused banner are not rendered; because `runActive` is false the Start button is enabled, and clicking it starts a new Phase A whose `wipe_old_runs` deletes the paused run's directory (about 8 minutes of SIM-T pull plus the per-ticket approval scan in the real run). Severity: low–medium — silent loss of the paused Phase A data and no way to resume it from the page. Code-verified.

1.10 WHEN a run ends with a non-zero exit code that is not a lane failure recorded as `publication_blocked` — a `fill_recalc` or `read_back` stage error, or an unhandled Phase B exception — and ADS was approved (`partial` false) THEN the system leaves the result banner on its previous text ("Run in progress… verification happens automatically at the end." or the earlier "Paused — upload…") and the start-state on "Running the full pipeline…", because `app.js renderFinish` has no terminal failure branch and `tick()` only updates the start-state when `status.stopped`; the failure is visible only in the log tail. Severity: low — latent hard crash of Phase B (no wrong data); 0 occurrences in the real run's 1494 rows. Code-verified; trigger needs live data.

Severity: low — silently incomplete output in PARTIAL runs. Code-verified.

1.13 WHEN a run was started without ADS approval (`_build_ads_flags` → `--skip ads --allow-partial`, `partial` true, no `blank_sources`) and the workbook is downloaded THEN the system publishes it as `Templete_OOJ Process_<Month>_KABIDEBA1_<stamp>.xlsx` without the `PARTIAL_` tag (`publish_to_desktop` derives the tag from `blank_sources(summary)` only), shows the banner "PARTIAL — workbook ready to download. Blank source(s): none" although the ADS sheet is blank, and the Start card's hint and start-state say "no download will be produced" although a download is produced. Code-verified and evidence-verified.

### Expected Behavior (Correct)

2.1 WHEN a Working Sheet row reaches the AF→AG→Valid block of the combined column-P formula and column AF (or AG) is a `#N/A` error THEN the system SHALL treat the error exactly as `remark_rules.decide_remark` treats a non-matching value — fall through to the AG check and then to "Valid" — so that column P never evaluates to `#N/A`, the 48 affected rows of a run like 2026-10-28 read "Invalid - It is Inside Jurisdiction as per GCRS Tool" (38) and "Valid" (10), and the formula still embeds the template body verbatim so `read_back`'s containment check continues to pass.

2.2 WHEN the GCRS/SIW `State` field holds a recognised 2-letter state code (at least `PB`, `DL`, `KL`, `TG`/`TL`, `BR`, `MH`, `HR`, `RJ`, `GJ`, `KA`, `TN`, `WB`, `UP`, `UK`, `MP`, `CG`, `OD`, `AS`, `JH`, `HP`, `JK`, `CH`, `GA`, `PY`, `AP`) THEN the system SHALL map it to its PIN zone and SHALL NOT report a mismatch when the zone agrees with the PIN; and WHEN the `State` field does not name any known state or code (a city/district such as "Bengaluru" or "Dehradun") THEN the system SHALL skip the zone consistency rule for that row rather than emit a `does not serve` MISMATCH, so that the real run's 69 false verdicts become OK/NOT OK verdicts and only genuine zone contradictions remain MISMATCH.

2.3 WHEN the local web server starts or restarts THEN the system SHALL leave `SearchResults*.csv` in `~/Downloads` untouched (it is now the operator's manual SCC export) while still removing the PNAMA/DSR QuickSight leftovers (`SWA_repeat_Prox_Pnam*`, `DSR_Raw_data*`) and everything under `_browser_downloads`.

2.4 WHEN a fresh run starts THEN the system SHALL wipe only the OOJ pipeline's own prior run folders and per-source capture artifacts (`runs/`, `tickets/`, `eagle/`, `pnama/`, `dsr/`, `polygons/`, `polygon_local/`, `ads/`, `scc_uploads/`) and SHALL preserve the post-comments feature's uploads, dry-run summaries and `post_comments_report.xlsx` files, and SHALL refuse to start while a post-comments subprocess is running.

2.5 WHEN Phase A exits with a non-zero code or without producing `tech_data.csv`/`tids.txt` THEN the system SHALL mark the run as failed (not paused): `/status` SHALL report a terminal failed state with the exit code, `upload_scc_csv` SHALL reject uploads with a clear reason until a new run is started, and the page SHALL show the failure, stop polling, and re-enable Start.

2.6 WHEN the operator uploads the SCC CSV and Phase B is about to start THEN the system SHALL re-run the preflight checks (Midway session valid, Edge automation profile free, template present) and refuse to resume with the same clear messages Phase A gives while the condition persists; and the post-comments feature SHALL treat a paused OOJ run (`_phase` in `awaiting_scc_upload`/`scc_uploaded`) as busy so a live posting run cannot start during the pause.

2.7 WHEN Phase B starts in an existing run directory THEN the system SHALL load the existing `summary.json` into `Run.summary` (keeping `preflight`, `tickets` and the `tickets` counts) before writing progress, so the SIM-T Tickets card stays `done` with its ticket/row counts for the rest of the run and in the final state.

2.8 WHEN the run is paused awaiting the SCC upload THEN the system SHALL offer the operator a way to abandon the run from the page: Stop SHALL be enabled, `/stop` SHALL succeed (HTTP 200, `stopped: true`) and reset the controller to idle, and Start SHALL be re-enabled afterwards.

2.9 WHEN the page loads while the controller already has an active or paused run THEN the system SHALL attach to it (start polling `/status`, render the cards, log, paused banner and SCC upload control) and SHALL keep Start disabled until that run is finished or explicitly stopped, so a reload never silently discards a paused Phase A.

2.10 WHEN a run ends with a non-zero exit code for any reason other than a recorded `publication_blocked` THEN the system SHALL show an explicit failure banner (including the failing stage or exit code) and update the start-state, instead of leaving "Run in progress…" or "Paused…" on screen.

2.11 WHEN a ticket has no parseable `createDate`/`lastUpdatedDate` THEN the system SHALL write an empty field to `tech_data.csv` (as `tickets_pull.write_outputs` already does) and `load_tech_data` SHALL read it back as `None`, so Phase B never crashes on a date field.

2.12 WHEN tech rows are available THEN the system SHALL write the "Approval in Comments" header (AI1) and every row's value regardless of whether polygon rows exist, keeping AG (polygon status) and AH (CX Address Check) logic unchanged.

2.13 WHEN a run was started without ADS approval THEN the system SHALL publish the Desktop file with the `PARTIAL_` tag, the PARTIAL banner SHALL name `ads` as a blank/skipped source, and the Start-card hint and start-state SHALL say that a partial (PARTIAL-labelled) download will be produced.

2.14 WHEN `write_polygon_rows` writes to the empty template sheet THEN the system SHALL place the header in row 1 and data from row 2, and SHALL write digit-only Tracking IDs with the same type rule as every other source sheet (`num()`), so the sheet's own A:C lookup matches Working Sheet D.

2.15 WHEN `scan_approvals` fails for one or more tickets THEN the system SHALL still write `""` for those tickets but SHALL count the failures, log the count (and the first error) through `run.log`, and record it in `run.summary["tickets"]` so a blank-by-failure column is distinguishable from a blank-by-content column.

2.16 WHEN the DSR export contains zero data rows THEN the system SHALL write `--out` with the canonical header (`tracking_id`, `zone`) and no rows, exit 0, and `lane_dsr` SHALL accept it as "no data" (blank Zone) exactly as it does for partially missing TIDs.

2.17 WHEN Phase A runs with `--tids-file` or `--max-tids` THEN the system SHALL write the exact, post-filter Tech_Data rows it will use to `tech_data.csv` so Phase B resumes with the same rows a single-shot run would have used.

2.18 WHEN `auto_setup.ensure_python_env` checks required packages THEN the system SHALL include `pandas` so the post-comments runner is importable on a fresh machine.

2.19 WHEN the page polls `/preflight` or `start_run` evaluates readiness THEN the system SHALL NOT launch a browser; the Playwright-Edge availability probe SHALL run at most once per server process (cached) or only on an explicit checklist request.

### Unchanged Behavior (Regression Prevention)

3.1 WHEN a Working Sheet row's AF holds one of the two transfer verdicts, or AG holds "Invalid - It is Inside Jurisdiction as per GCRS Tool", or the embedded template formula returns any non-`#N/A`, non-"LM to reattempt" value, or `J` is `#N/A` THEN the system SHALL CONTINUE TO produce, respectively, the AF text, the AG text, the template's own value, and "Invalid- Incorrect TID / TID Not Found" through a visible column-P formula that embeds the template body verbatim (array kind preserved, `_xlfn.` kept, under 8,192 characters) and passes `read_back`'s containment check.

3.2 WHEN the GCRS `State` field names a full state (e.g. "Karnataka", with small typos tolerated) whose zone matches the PIN, or the address is junk/too thin, lacks a PIN, has a malformed PIN, or SIW confidence is low/medium/unknown THEN the system SHALL CONTINUE TO return the existing OK / NOT OK / MISMATCH verdicts of `analyze_cx_address`, and the CX column SHALL CONTINUE TO never influence the Inside/Outside status or the Remark.

3.3 WHEN the server starts or restarts THEN the system SHALL CONTINUE TO delete `_browser_downloads` contents, `.crdownload/.tmp/.partial` and atomic-write sidecars under `tools/captures`, and PNAMA/DSR QuickSight leftovers in `~/Downloads`, and SHALL CONTINUE TO never touch source, docs, the template, tests or any other Downloads/Desktop file.

3.4 WHEN a fresh run starts THEN the system SHALL CONTINUE TO delete all prior OOJ run folders and per-source OOJ capture artifacts regardless of age, keep the current run directory and `scc_enum_map.json`, and prune only `Templete_OOJ Process_*.xlsx` Desktop exports whose modification date is before today.

3.5 WHEN Phase A completes successfully THEN the system SHALL CONTINUE TO exit 0 before the SCC stage, print `RUN_DIR=` first, write `_latest.txt`, `tech_data.csv` (12 columns including `approval_in_comments`) and `tids.txt`, and the controller SHALL CONTINUE TO enter `awaiting_scc_upload`, render the upload control inside SCC card 2 while preserving the chosen file across polls, accept a valid CSV, and auto-continue Phase B in the same run directory with the same ADS/partial flags.

3.6 WHEN Phase B runs THEN the system SHALL CONTINUE TO execute SCC (upload) → EagleEye (API, concurrent) → PNAMA → DSR (serial on the one Edge profile, 2 attempts with one refresh) → GCRS (sequential `/grbi`, mcscli first, Edge fallback once) → Polygon (single fetch per station, no retry, realtime refresh) → ADS (single file, first column `TrackingId`) → fill/recalc → read_back, with the existing row-alignment, TID-identity and polygon-verification contracts, and SHALL CONTINUE TO never wipe in Phase B.

3.7 WHEN all required lanes, `fill_recalc`, `read_back` and the polygon verification succeed in an ADS-approved run THEN the system SHALL CONTINUE TO mark the run publishable and downloadable, publish `Templete_OOJ Process_<Month>_KABIDEBA1_<stamp>.xlsx` to the Desktop, and `_existing_desktop_copy` SHALL CONTINUE TO find it by stamp; a run with blank sources under `--allow-source-failures` SHALL CONTINUE TO be downloadable with the `PARTIAL_` tag; a run with `publication_blocked` SHALL CONTINUE TO be neither.

3.8 WHEN the page is used THEN the system SHALL CONTINUE TO expose every existing `preflight_state()` and `get_status()` key unchanged (new keys may be added), keep every element id referenced by `app.js` present in `index.html`, keep the KABIDEBA credit in the header, footer, title and server banner, and the Stop button SHALL CONTINUE TO abort a live Phase A/Phase B process tree.

3.9 WHEN tech rows, polygon rows, SCC/EagleEye/PNAMA/DSR/GCRS/ADS rows are written to the template THEN the system SHALL CONTINUE TO write them to the same sheets and columns (Tech_Data A–L with the `Put the Quip data ` header left as is, Working Sheet AG/AH/AI literals row-aligned to `tech_rows[r-2]`, `COLUMNS_TO_REMOVE == []`, no column deletion or shift), and `read_back` SHALL CONTINUE TO enforce the 25-column `FINAL_COLUMNS` header contract, TID alignment, polygon alignment and the non-`#N/A` Excel-error check.

3.10 WHEN `scan_approvals` succeeds THEN the system SHALL CONTINUE TO make exactly one `get-ticket` CORRESPONDENCE call per ticket, label hits "Site clear"/"Approved" in first-seen order, carry the value to every exploded TID row, and round-trip it through `tech_data.csv` into Working Sheet AI and Tech_Data L.

3.11 WHEN the sanitizer, the wipe, `load_scc_csv`, the lanes or the fill encounter a locked or missing file THEN the system SHALL CONTINUE TO fail loudly for data-bearing stages (stage marked error, run blocked or PARTIAL) and never silently drop or reorder a Tech_Data row.
